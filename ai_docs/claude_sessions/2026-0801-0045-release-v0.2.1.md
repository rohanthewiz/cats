## What the repo looked like going in

|---|---|

| GitHub releases | none at all |
| `.github/workflows/release.yml` | fires on `v*` tags, matrix of 3 runners, never triggered |

So `v0.1.0`'s annotation still read `herdr-web v0.1.0 — first all-Go release

release build against an old commit, so it was left alone at that point.

118 commits sat between `v0.1.0` and `HEAD`: 49 `feat`, 18 `fix`, no

straightforward 0.x minor bump, confirmed with the user as **v0.2.0**.

## v0.2.0 shipped broken

Tagged, pushed, workflow fired for the first time ever. Result:

```
dist (ubuntu-latest)     => success
dist (ubuntu-24.04-arm)  => success
dist (macos-latest)      => FAILURE
```

`fail-fast: false` meant the two Linux tarballs still attached, so the release
published as a **partial** — Linux amd64 + arm64, no darwin.

### A tooling trap worth remembering

`gh run watch <id> --exit-status` **exited 0 on a run that failed.** The
background watcher reported success. Every subsequent check in this session
polled `gh run view --json jobs -q '.jobs[] | .name + " => " + .conclusion'`
instead, which reports per-job truth.

## Root cause: the test, not the product

`TestHydratePATHOnGUILaunch` in `cmd/catapp/shellenv_test.go` failed with
`exec: "go": executable file not found in $PATH`.

The bug was a conflation of two different environments:

- The **precondition** checked `exec.LookPath("go")` against the *test
  process's* PATH — which on a runner `setup-go` populates via `GITHUB_PATH`,
  inherited by the whole job.
- The **assertion** depended on the *login shell's* PATH — and a freshly
  spawned `zsh -ilc` sources only the user's rc files, which on a runner have
  never heard of the toolchain.

The precondition was satisfiable exactly where the assertion was not, so the
build failed on a machine where PATH hydration was working correctly.

### The second discovery: `loginShellPATH` is not pure

The first fix attempt read the expected PATH *before* `t.Setenv("PATH", bare)`
and **failed locally**:

```
login shell entry "~/go/pkg/mod/golang.org/toolchain@v0.0.1-go1.26.0.darwin-arm64/bin"
missing after hydration
```

The shell that `loginShellPATH` spawns **inherits the caller's PATH**, and the
customary rc-file line `export PATH="$HOME/bin:$PATH"` folds that inherited
value back into what comes back. So two calls under different PATHs return
different results — under `go test`, the toolchain directory the test binary
runs with leaks into the first reading and not the second.

The expectation must therefore be derived *after* PATH is set to the
launchd-bare value, under the same environment `hydratePATH` will see. This
non-purity is a real property of the function and is now documented at the call
site.

### The shape of the fix

The contract is now stated against the login shell's **own** PATH — every entry
it reports must survive into the merged result — rather than against any one
tool. The `go` lookup remains but only `t.Logf`s: it describes the environment,
not a defect.

Verified three ways:

1. `make test-ghostty` fully green locally.
2. The test passing under a stubbed `$SHELL` emulating a login shell with no Go
   toolchain (the CI condition) — logs instead of failing, while still proving
   the shell's entries survive.
3. The real macOS runner going green on the next release.

Commit: `b7e5082 fix(test): the PATH hydration test stops asking CI for a
toolchain it never had`

## Release bodies were empty

Checking before deleting v0.2.0 turned up that **both** release bodies were
blank. `softprops/action-gh-release` does not carry an annotated tag's message
into the release body — the API takes the two from different places. The
changelogs written into the tag objects were never visible on the releases
page, and v0.2.1 had shipped with no notes at all.

Fixed by writing the full grouped changelog (Plugins / Workspaces and tabs /
Interface / macOS app / CLI / Docs) onto v0.2.1 with
`gh release edit --notes-file`, including a note that v0.2.0 was withdrawn with
no product differences between them — so deleting v0.2.0 would not orphan the
reference v0.2.1's notes made to it.

## Cleanup performed

| Action | Result |
|---|---|
| `gh release delete v0.2.0 --yes` | releases page shows only v0.2.1 |
| `git push origin :refs/tags/v0.2.0` + `git tag -d v0.2.0` | gone remote and local |
| `git tag -d v0.1.0` | gone (was never pushed) |

Both tag messages were backed up to the session scratchpad first. `git describe`
now resolves `v0.2.1-1-g5599fb3` cleanly.

**Consequence:** with `v0.1.0` gone, `git describe` on any commit older than
`v0.2.1` falls back to a bare hash, so `make dist` on an old checkout stamps a
`dev`-style version. Only matters when building from history.

## Workflow changes

### `generate_release_notes: true`

Verified against the action's source rather than assumed, because a wrong
answer would silently blank notes on every future release. Two facts made it
safe for a 3-job matrix hitting the same tag:

- The update path resolves `body = workflowBody || existingReleaseBody`, so
  later jobs **preserve** what the first wrote instead of overwriting empty.
- `generate_release_notes` is passed on both create and update, but only the
  create endpoint honours it — the update is a no-op for notes.

Whichever platform finishes first creates the release and generates notes; the
rest just attach tarballs.

Commit: `5599fb3 ci(release): the release writes its own notes instead of
shipping a blank body`

### Intel macOS runner

The request named `macos-13` — **it is retired** and absent from
`actions/runner-images` entirely, so that label would have failed the job with
an unresolvable runner rather than producing Intel builds.

Substituted **`macos-15-intel`** after confirming:

- It is a **standard** runner, so free and unlimited — this repo is public.
  (The `-large` Intel variants would have been billed.)
- Chosen over `macos-26-intel` deliberately: binaries link against the SDK of
  whatever builds them, so the older macOS keeps the deployment floor lower for
  the Intel users who are the point of the exercise.

Checks that came out clean:

- **No cache collision** — the key includes `runner.arch`, so `macOS-X64` gets
  its own Zig entry rather than restoring the arm64 toolchain into an Intel job.
- **No filename collision** — `DIST` derives from `go env GOARCH`, producing
  `cats_vX_darwin_amd64.tar.gz`.
- **`scripts/build-libghostty-vt.sh` already supports Intel** — it has a
  `Darwin/x86_64 → x86_64-macos` case with its own pinned Zig SHA.

Note: the arm64-SDK-patch block in that script is gated on `Darwin` broadly,
not on arm64. On Intel it does unnecessary work — the perl only rewrites
`arm64e-macos` occurrences and leaves x86_64 slices intact — so it is wasteful
but not harmful. Left as-is.

## Open items

- **The first Intel run is unverified.** `release.yml` only fires on `v*` tags,
  so it cannot be exercised without cutting a release — the same blind spot
  that produced the v0.2.0 macOS failure. `ci.yml`'s ghostty job already
  matrixes `[ubuntu-latest, macos-latest]`; adding `macos-15-intel` there would
  give Intel signal on every push. **Not done** — offered, not yet requested.
- **`macos-14` is now flagged deprecated** in the runner images list and
  `macos-latest` has moved to macOS 26. Nothing here pins 14.
- **Generated notes are a flat commit/PR list**, with no grouping into
  Plugins / Interface / Docs the way v0.2.1 was written by hand. The pattern is
  to let the workflow publish generated notes, then layer a curated version on
  with `gh release edit --notes-file`.
