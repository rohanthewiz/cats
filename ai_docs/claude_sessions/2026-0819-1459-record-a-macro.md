## Part 2 — Phase 6c, record-a-macro

`catctl record start` → do the thing → `catctl record stop <name>` writes a
runbook. Everything downstream of that sentence existed since 6a/6b; the whole
phase was upstream of it.

### The journal is a wrapper, not a case

`Dispatch` became two functions. The exported one wraps the decoder and the
responder when the command is recorded and a recording is armed; the unexported
`dispatch` is the table, unchanged and unaware. No case knows it is being
recorded, which keeps "what a macro replays" the same question as "what the
command does". `TestCommandSpecsRouted` reads `dispatch` now, since that is
where the switch lives.

The recorder reaches the dispatcher through an **optional interface** on the
backend (`Recorder() app.Recorder`) rather than a Backend method. A recorder is
not something a dispatcher needs in order to run a command, and widening the
seam would have made every fake in the tree implement a method it has no use
for. It is read at construction because the runbook executor builds a dispatcher
per step — one set on the instance would have missed whichever site forgot.

### Three things the shape of the hook decided

- **The slot is taken on the way in and filled on the way out.** `Begin`
  reserves the position, `Commit` fills it, `Abort` releases it. Recording on
  completion alone would have silently reordered every macro containing a command
  that resolves late (a worktree create, a file put to another machine) against
  the sequence the user actually performed. A command that failed did not happen;
  a command that never resolves its responder is never emitted.
- **The params kept are the caller's raw bytes.** This is the 6b `omitempty` bug
  wearing its third hat: `submit: false` sent explicitly is invisible once it has
  been through a struct field that drops zero values, so a recording built from
  the decoded params turns "type this line" into "press Enter on it".
  `JSONParamDecoder` grew `RawParams`, and the wrapper prefers it.
- **Effects, and two exceptions in each direction.** `CommandSpec.Recorded` is
  the third dispatch property, declared per command. The rule is not "has an
  effect" but "would replaying this do again what was done", which puts
  `pane.wait_for_output` **in** (no effect at all; a replay without it races the
  shell it waited for) and three effects **out** — `ui.action`,
  `chat.permission`, `ledger.jump` each name something that existed for one
  moment. `runbook.run` is out because its *steps* are recorded as they re-enter
  `Dispatch`; recording the call too would replay every effect twice.

### Handles, and the anchor that makes the feature usable

The plan named this as the hard part and recommended refusing an unrewritable
pane. It was right that a literal pane id must never be emitted — replayed
tomorrow it types into somebody else's terminal — but a refusal alone would have
failed the *common* recording, which starts in a pane that already exists. So
there are three outcomes:

1. a pane or workspace produced **inside** the recording becomes a reference to
   the step that produced it (`{{ s1.pane }}`), with ids given only to steps
   something actually names;
2. the pane and workspace the recording **started in** become the pane and
   workspace the runbook is *run from*, through a `pane.get` / `session.get` step
   the emitter prepends. Both are ordinary §7 queries, so "the pane this was
   started from" needed no runbook-only concept — and neither is added unless
   something referred to it;
3. anything else is refused, naming the step, the id, the field and the fix.

Workspaces travel with panes because the argument is identical (`w3` in a fresh
session is somebody else's workspace) and the mechanism is one `kind` string.
Tab numbers are deliberately **not** handles: a tab number is a position, and
"the second tab" means the same thing twice.

### Redaction is per field, and narrow on purpose

`cats:"secret"` withholds the value and the emitter declares a var for it, so the
runbook keeps its shape and asks for the credential when it runs. Today that is
`host.attach`'s token and nothing else. `pane.send_input`'s text is the most
private field in the vocabulary and is recorded, because it is also the one a
macro exists to replay — the protection for it is that recording is armed at all.

The build-breaker the plan asked for is `TestRecordedParamsAreClassified`: an
exhaustive table of every field of every recorded command, cross-checked against
the tags in both directions, plus a second test refusing a `cats` tag on a
nested field. Classification is top-level only, and a tag nothing reads is
exactly the drift these tests exist to catch.

### Four things the writing and the live run found

- **The emitter has to load what it wrote.** `Emit` finishes by `Parse`ing its
  own output, so a recording that would not load is an error at record time
  rather than a broken file found next week. One call, and the only check that
  covers the whole document at once.
- **A refused stop must not throw the recording away.** The two ways stop fails
  are a name already taken and a handle that cannot be rewritten; discarding on
  either punishes a typo with the loss of everything recorded. The recording
  stays armed and the message says so.
- **Numbers cross two decoders here too.** Params arrive as a JSON tree where
  every number is a float64, and a YAML encoder writes `60000.0`. Harmless small,
  wrong for a file offset past 2^53, ugly in every case in a file whose
  readability is why it is YAML. Integral floats are written as integers and map
  keys sorted, which is also what makes emission byte-stable.
- **An empty recording is an answer, not a file.** Stopping with nothing captured
  is refused rather than writing a stepless document, and `status` exists so that
  state is visible *before* stop is typed — a recorder that captured nothing
  (every command a query) is otherwise indistinguishable from one that works.

Coalescing landed as planned with one rule the plan left open: a run of
`pane.send_input` merges up to **and including** the call that submitted, because
submit is an Enter encoded against the pane's live mode state rather than a
newline in text.

## Verified live

One cathost, one catway, `catctl`, an isolated `XDG_CONFIG_HOME`:

```yaml
name: hello-flow
steps:
- id: s1
  run: pane.split
  params: {direction: v}
- run: pane.send_input
  params: {pane: "{{ s1.pane }}", submit: true, text: echo HELLO-FROM-RECORDING}
- run: pane.wait_for_output
  params: {pane: "{{ s1.pane }}", pattern: HELLO-FROM, timeout_ms: 5000}
- run: ui.notify
  params: {title: recording done}
```

`catctl runbook hello-flow` then created pane 3, and `catctl capture 3` showed
`HELLO-FROM-RECORDING` in it. A recording made in an existing pane emitted the
`pane.get` anchor and `{{ start_pane.pane }}`. A `host.attach` carrying a token
emitted `token: "{{ vars.token }}"` with the var declared and the description
saying a value was withheld — a grep for the token over the runbook directory
found nothing, while the address and fingerprint beside it were recorded
verbatim. A `host.attach` that FAILED its fingerprint check left the recording at
one step, which is the abort path seen from outside. A `send_input` to a pane
neither created by the recording nor started in was refused by name, with the
recording still running afterwards. Completion offers the four actions; `catctl
help` shows the verb.
