## The correction

Phase 6e's commit message and docs said the control API was "a duplex protocol
rather than the hook API's one-shot line, so carrying it across the seam is its
own piece of work". That was wrong, and the design only came into focus once it
was corrected.

The **base** control protocol is one newline-framed request and one newline-framed
response, then close — the hook relay's shape exactly. What it actually has is a
*streaming method*: `events.subscribe` writes an ack and then pushes `Event`
frames for as long as the caller stays connected.

So the difficulty was never duplexity. It was that the relay could not assume
"one request, one reply, close", because one of the methods is a conversation.
That single fact produced the whole shape:

- the relay carries a **connection**, not a message pair:
  `control_open` / `control_data` / `control_reply` / `control_close`
- a **client hanging up has to travel across**, because that is precisely how a
  subscription is cancelled — a streaming client sends nothing else, so its
  disconnect is the only signal there is

Worth remembering as a habit: the sentence justifying why something is hard is
worth re-reading before building around it.

## The idea the implementation is

Rather than reimplement dispatch behind the relay, the relayed frames become a
synthetic `io.ReadWriteCloser` handed to `ctlproto.Server.ServeConn` — the same
entry point a real socket goes through.

```
cathost socket ──▶ control_open/_data ──▶ relayConn.Read
                                            │
                                   ctlproto.Server.ServeConn
                                            │
relayed client ◀── control_reply ◀──── relayConn.Write
```

`relayConn` is ~60 lines: a buffer with a `sync.Cond`, reads that block until
more bytes arrive or the connection closes, writes that go out as
`control_reply`. That is all that was needed, because everything else — the
command table, `events.subscribe`, the per-request backstops, the
`pane.wait_for_output` special case, the cancellation — is the server's already.

The cost on the `ctlproto` side was `ServeConn` plus widening two signatures
(`handleStream`, `pump`) from `net.Conn` to `io.ReadWriteCloser`/`io.Writer`.
Both are honest independently: nothing in that server ever used an address or a
deadline.

The argument for doing it this way is not tidiness. A second dispatch
implementation would agree with the first until the day it didn't, and the thing
it would be disagreeing about is *who may run commands against every pane in the
session*.

## Permission, which is most of the design

The relay hands a machine that is not this one the ability to drive the whole
session. Three decisions:

**1. Advertising the socket is not permission.** The cathost always opens its
relay socket and puts the path in the welcome. Whether anything arriving on it is
honoured is `config.Host.ControlRelay`, per host, default off. The daemon
offering the capability is exactly the party that should not get to decide it.

**2. The gate is checked when a connection ARRIVES, not when a pane's
environment is written.** This is the whole security story and it took a moment
to see:

- the env var is a convenience — it tells in-pane tooling where to dial
- turning the flag off cannot unset it in panes that are already running
- the socket on the far machine goes on existing either way

So the environment *cannot* be the boundary, and the arriving-connection check
must be. A consequence worth having: turning the flag off is effective
immediately, on panes that were told the path while it was on.

**3. No denylist of "sensitive" methods.** The tempting move was to refuse `pair`
and `clipboard.read` over the relay. The codebase had already written down why
that is theatre, in `ctlproto.MethodClipboardRead`'s own doc: a caller holding
the socket can `pane.send_input` `pbpaste` into a local pane and read the answer
back with `pane.capture`. Gating the direct route gates nothing it does not
already have by a longer one — and it makes the honest path look more privileged
than the dishonest one.

Which means the only honest statement is the all-or-nothing one, so that is what
the docs say: enabling this for a host grants that machine every command, on
every host, including panes it cannot otherwise see. Enable it for a machine you
trust as much as the one running catway.

Two smaller ones in the same spirit: disabling `server.control_socket` disables
the relay too (one switch, not two), and `cathost -control-socket -` lets a
machine refuse from its own side.

## What thinking about the blast radius found

Working out what the relay grants surfaced an escalation **already shipped** in
6e: a relayed hook report could name a pane on another host. Pane handles are
session-wide and `applyHookReport` never consulted the reporting host, so one
compromised box could mislabel every agent in the session — including panes it
cannot see.

Now scoped: a relayed report may only address panes on the host that relayed it;
the local socket keeps its full reach. The refusal is `pane_not_found` rather
than "not yours", because the relaying host has no business learning which panes
exist elsewhere. Nothing legitimate is lost — these hooks run inside panes, and a
pane's hooks are on the pane's machine.

The general shape: adding a privileged path is a good moment to audit the
adjacent one that shipped last week.

## Live verification

Three cathosts, one catway, one host trusted — the third existing only to be
refused.

- flag off everywhere: a request written straight into a cathost's relay socket
  is refused and logged **by host id**
- `control_relay: true` for devbox + `catctl reload`, no redial: a pane created
  there gets `CATS_CONTROL_SOCKET=/tmp/cats-ctlrelay-…`, and in-pane `catctl
  ping` / `catctl panes` answer from this catway
- **the streaming half, which is the one worth proving**: `catctl events` running
  *inside a devbox pane* received `pane_added` / `pane_cwd` for a pane created on
  the **local** host; killing the in-pane process stopped it (the cancel reaching
  catway as a close); a fresh subscription afterwards worked
- the untrusted host's pane reports `CATS_CONTROL_SOCKET=-`, and its `catctl`
  prints the reason and the flag to set

## Two self-inflicted detours worth remembering

- `printf … | nc -U <relay>` came back empty and briefly looked like a broken
  relay. `nc` had gone before the reply arrived. The real test — in-pane
  `catctl` — worked first time. When the harness is improvised, suspect the
  harness before the feature.
- `pkill -f "catctl events"` sent as pane input killed the *outer* shell, whose
  own command line contained that string inside the `--params` JSON. Exit 144
  with no other explanation. Used `kill %1` instead.

## Odds and ends

- `catctl events` emits pane lifecycle events, not pane output; the first
  cancellation test looked like a failure because the stimulus (`echo`) produces
  none. Splitting a pane is a good trigger.
- `applyHookReport` kept its 2-arg signature as a wrapper over
  `applyHookReportFrom`, so 14 existing call sites stayed untouched and the
  naming mirrors `answerHookFrom`.
- The `hosts` roster diff (`sameDialTarget`) deliberately excludes
  `control_relay`, so flipping it does not drop the connection; `applyHostRoster`
  already refreshes a kept host's `spec`, which is what makes the live gate read
  the new value.
