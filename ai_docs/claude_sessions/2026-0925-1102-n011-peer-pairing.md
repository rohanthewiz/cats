# Session: peer pairing — `catctl pair peer` grants replace copied passwords (N-011)

Session ID: 1c49896f-b5c4-4078-b225-4cd93952e60f
Date: 2026-09-25

## 1. The ask

The user pasted next-list item **N-011**:

> `catctl attach-peer` takes only a token *file*. A `pair`-style grant for
> peers (short-lived, revocable) would avoid copying passwords.

## 2. The design fork

Device pairing (`catctl pair`) already existed. It mints a 5-minute,
single-use token that a phone redeems at `/login` for a **session**. Sessions
last `--session-ttl` (default 24h) and die when catway restarts. That's fine
for a phone, but a peer that has to re-pair every day and after every restart
would be worse off than one holding the password.

I asked the user to choose between:

- **Durable grant** (recommended): a peer pairing token redeemed for a
  long-lived peer credential that is stored as a hash on the grantor, scoped
  to `/peer/v1/*`, and revocable one peer at a time.
- **Session-based**: reuse the existing flow as-is. Small, but it expires daily
  and on restart, and the only way to revoke is a restart.

The user chose the **durable grant**.

## 3. What was built (commit `6d01456`)

```
B: catctl pair peer [label] ─socket─▶ IssuePeerPairToken (5 min, single use, kind=peer)
        prints: catctl attach-peer <id> 'cats://peer?f=…&t=…&u=…'
A: catctl attach-peer bee '<link>'  → peer.attach {url, pair_token, fingerprint}
   A's catway ── POST /peer/v1/pair {token, name} ──▶ B: RedeemPeerPairToken → peergrant.Mint
   ◀── {credential "catspeer_…", grant_id, instance}
   writes <state_dir>/peer-tokens/bee.token (0600), then the peers: entry (token_file)
```

- **`internal/peergrant`** (new): a btypedb store keyed by grant id, holding
  only the SHA-256 of each credential. An in-memory hash→grant map makes the
  per-request check a map lookup. Mint, Check, List and Revoke are all written
  to disk before memory (SyncAlways, so a revoke can't be lost). `LastUsed`
  is persisted at most hourly. Labels are cleaned of control characters and
  capped at 64 runes.
- **`gwauth` pairing kinds**: `pairStore` values became
  `pairGrant{expires, kind, label}`. `RedeemPairToken` accepts only device
  tokens and the new `RedeemPeerPairToken` only peer tokens. A token presented
  at the wrong endpoint is left unspent.
- **catway auth guard**: `/peer/v1/pair` is public, like `/login` (the token in
  the body is its credential). `peerAuthed` accepts a grant only when the path
  has the `/peer/v1/` prefix. `authed()` never looks at grants, so a grant
  can't open `/ws`.
- **Control socket**: these are transport methods, not §7 commands, so a
  browser session can't manage peer access. `pair` takes optional
  `PairParams{peer,label}` and `PairInfo.kind` is `"peer"`. New methods:
  `peer.grants` (list) and `peer.revoke` (by id). They are answered in
  `controlDispatch` before the dispatcher sees them.
- **`peer.attach` with `pair_token`** (`attachPeerByPairing`): everything that
  can be checked locally is checked before the round trip, because the round
  trip spends the token. The redeem runs on a goroutine. The token file is
  written atomically at 0600, then the config is saved on the loop. An id that
  is already attached is re-paired in place, keeping its label, and a literal
  `token` left over from the password flow is cleared. A failed save removes
  the new file.
- **`detach-peer`** deletes the token file only when it lives under
  `<state_dir>/peer-tokens`, and logs that the grant is still live on the peer.
- **`peersync`**: `PathPair`, `PathPrefix`, `PairRequest`/`PairResponse`,
  `Client.Redeem`, and `PeerLink`/`ParsePeerLink`/`IsPeerLink`. The scheme is
  `cats://peer`, deliberately separate from the mobile app's `cats://pair`.
  An unquoted link cut at `&` gets an error that asks "was it quoted?". A 401
  now has separate messages for a refused pairing token and a refused
  credential.
- **catctl**: `pair peer [label...]` prints a ready-to-paste, single-quoted
  `attach-peer` command. `attach-peer` accepts a link in place of the URL and
  refuses a link plus a token_file. The new verbs `peer-grants` (a table) and
  `revoke-peer-grant` are wired up, along with shell completion (`pair` →
  `peer`) and help text.
- **Peers dialog** (`43-peers.js`): the url field also accepts a
  `cats://peer` link.
- **wire**: `PeerAttachParams.PairToken` (`cats:"secret"`), classified as
  secret in `record_test.go` so recorded runbooks never store it.
- **orch.stateDir**: resolved once in main (`state_dir`, or the XDG default).
- **Docs**: `cli.md` ("Pairing a peer"), `peer-sync.md` (Trust rewritten plus
  a new "Pairing" section), `auth-and-tls.md` ("Peer grants"),
  `control-api.md` (transport methods now number six), `config.example.yaml`,
  and the `config.Peer` comment.

## 4. Verification

- `go test -race -tags ghostty ./...` passes. New tests:
  - `peergrant`: mint/check, rejects, revoke, surviving a reopen, ordering and
    label cleaning, the LastUsed throttle.
  - `gwauth`: kind separation and peer-token expiry.
  - `peersync`: link round trip and rejects, and `Redeem` against httptest.
  - catway: the full lifecycle through rweb synthetic requests, with the
    grant refused on `/ws` and `/`; device tokens refused at the peer
    endpoint; no store; `withPairedPeer`; managed token files.
  - catctl: `pairParams`, the peer render parsing back through `attach-peer`,
    and the grants table.
- **Two-catway loopback smoke test** (see the two-catways memory): A over
  http on :9431, B over https on :9432 with an openssl test certificate, so
  the fingerprint in the link was exercised. Checked: pair → attach → sync,
  token file at 0600, a reused link refused with 401, the grant getting 200
  on `/peer/v1/hello` but 401 on `/ws` and 302 on `/`, B restarted (the grant
  loaded from disk, sync OK), revoke → sync refused, re-pair of the same id →
  sync OK, detach → file and entry gone.
  - The Unix socket paths under the scratchpad exceeded macOS's 104-byte limit,
    so the sockets went to `/tmp/cn011`, which was removed afterwards. Only the
    four PIDs started for the test were killed.
  - B was bound to 127.0.0.1, so its link advertised the LAN IP, as device
    pairing already does. The test rewrote `u=` to loopback. With a real
    wildcard bind this doesn't come up.
